# ADR-007: Стратегія ключів — partition key визначає шард, sort key впорядковує всередині

- **Status:** Accepted
- **Date:** 2026-11-05
- **Milestone:** M2 (обов'язковий ADR «Partition key strategy»)

## Context

Запис має первинний ключ. Треба вирішити:
1. що саме хешується для вибору шарда;
2. чи підтримуємо складений ключ (partition key + sort key) — в завданні він опційний;
3. як уникнути «гарячих» шардів.

Лекції 4 і 8:
- **partition key має бути висококардинальним** (багато різних значень);
- **поганий ключ шардингу** концентрує дані: приклад з декадою народження студентів КПІ;
- **DynamoDB:** `hash(partition key)` → партиція; sort key впорядковує записи всередині партиції.

## Options

### A) Лише partition key
- ➕ Найпростіше.
- ➖ «Усі замовлення користувача 42» — або окремі ключі (розлітаються по шардах → опитувати всі), або один великий запис-список (переписується повністю при кожній зміні).

### B) Partition key + опційний sort key, хешуємо лише PK (як DynamoDB)
- ➕ Записи з однаковим PK лежать на одному шарді, впорядковані за SK → діапазонні запити (Query) йдуть до одного шарда.
- ➕ Таблиця без SK працює як варіант A.
- ➖ Усі записи одного PK — на одному шарді: дуже великий або гарячий PK не розділиться.

### C) Хешувати PK + SK разом
- ➕ Найрівніший розподіл.
- ➖ Записи одного PK розлітаються → Query мусить опитувати всі шарди; sort key втрачає сенс.

## Decision

**Обираємо B.**

- **Визначення таблиці:** `name`, `partitionKey` (ім'я атрибута), `sortKey` (ім'я атрибута, опційно). Ім'я таблиці — `[A-Za-z0-9_-]{1,64}`.
- **Ключ на кільці:** `"{table}#{pk}"`. Ім'я таблиці не може містити `#`, тож межа однозначна навіть якщо `#` є в PK.
  Ім'я таблиці входить у ключ, щоб однакові PK різних таблиць (`users/42`, `orders/42`) не потрапляли завжди на один шард.
- **Sort key не хешується.** На шарді записи одного PK впорядковані за SK.
- **Типи:** PK і SK — рядки, порівняння SK — побайтове (лексикографічне), як рядки. Дати — у форматі ISO 8601 (`2026-11-05`), тоді лексикографічний порядок = хронологічний.
- **YCSB:** таблиця `usertable`, PK = ключ YCSB (`user<n>`), без SK — висока кардинальність, рівномірний розподіл.

## Чому (докладно)

1. **Query за одним шардом.** «Замовлення 42 з 1 по 5 листопада» = один запит до одного шарда, а не до всіх.
2. **Сумісність з A.** Таблиця без SK поводиться як простий KV; YCSB саме так і працює.
3. **Як у DynamoDB** — модель, яку курс розбирає на лекціях 4 і 8; відповідь на контрольне питання 5.
4. **C ламає сенс sort key** — впорядкування в межах PK неможливе, якщо записи PK на різних шардах.

## Consequences

**Отримуємо:**
- складений ключ (опційна частина завдання 1);
- Query за діапазоном SK;
- рівномірний розподіл за умови висококардинального PK.

**Платимо:**
- **гарячий або дуже великий PK** (наприклад, `tenant=big-company`) навантажує один шард. Захист у M2 — лише рекомендація обирати висококардинальний PK; автоматичний split гарячих ключів — тема M5 (ребаланс) і бонусного кешу;
- лише рядкові ключі (DynamoDB має ще number і binary) — свідоме спрощення;
- лексикографічний порядок SK: числа треба доповнювати нулями (`007` < `010`), інакше `10` < `7`.

**Що відкинули і чому:**
- **A** — без діапазонних запитів, «список у записі» або опитування всіх шардів.
- **C** — руйнує локальність PK, Query по всіх шардах.

## Де це в коді

- `api/openapi.yaml` — `POST /tables`, адреси з `{pk}` і `{sk}`, Query.
- Coordinator: ключ на кільці `"{table}#{pk}"`.
- Шард: записи згруповані за `(table, pk)`, впорядковані за SK при Query.
