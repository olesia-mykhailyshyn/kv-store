# ADR-002: Структура стеків — мережа окремо від IAM і застосунку

- **Status:** Accepted
- **Date:** 2026-10-31
- **Milestone:** M1 (обов'язковий ADR «Stack layout: one stack, or network separate from application»)

## Context

Уся інфраструктура описується в CloudFormation (ADR-001). **Стек** — група ресурсів, яку CloudFormation створює з одного шаблону і видаляє разом. Треба вирішити, скільки стеків і що в якому лежить.

Обмеження, які впливають на вибір:

- **Стек атомарний: «усе або нічого».** Якщо хоч один ресурс не створився, CloudFormation відкочує (`ROLLBACK`) і видаляє все, що вже встиг створити в цьому стеку.
- **CloudFormation створює ресурси з правами того, хто запускає деплой** (у нас — сесія ролі `voclabs`), якщо стеку не дати окрему service role.
- **Пісочниця не дає створювати IAM-політики й ролі** (умова завдання; доказ збираємо в завданні 1). Тому IAM-ресурси M1 можна лише описати і перевірити, але не задеплоїти.
- **Мережа змінюється рідко, застосунок (з M2) — часто.** У M2 з'явиться CI/CD, що деплоїтиме застосунок автоматично.
- **Завдання 8:** знести все і підняти з IaC, заміряти час.

## Options

### A) Один стек на все
Мережа, IAM і з M2 застосунок — в одному шаблоні.
- ➕ Один файл, одна команда.
- ➖ **Не деплоїться в пісочниці:** IAM-ресурс отримує AccessDenied → увесь стек, разом з уже створеною VPC, відкочується.
- ➖ Кожна зміна застосунку оновлює стек, у якому лежить мережа: помилка в коді шардів може зачепити VPC (великий **blast radius**).

### B) Окремі стеки за життєвим циклом
`kv-network` (мережа), `kv-iam` (IAM, лише валідація), з M2 — стеки застосунку, які беруть ID мережі з її Outputs.
- ➕ Мережа деплоїться незалежно від IAM.
- ➕ Малий blast radius: стек застосунку можна видалити або зламати, не чіпаючи мережу.
- ➕ Кожен стек — окрема тема для захисту (мережа, IAM, застосунок).
- ➖ Кілька файлів; стеки залежать один від одного, тож видаляти треба в правильному порядку.

### C) Nested stacks
Батьківський стек, усередині — дочірні.
- ➖ Шаблони дочірніх стеків треба класти в S3-бакет — додатковий ресурс і крок.
- ➖ Ще один шар для пояснення; для 2–3 стеків вигоди майже нема.
- ➖ Падіння дочірнього стека (IAM) все одно відкочує батьківський — проблема варіанта A лишається.

## Decision

**Обираємо B — окремі стеки за життєвим циклом.**

| Стек | Шаблон | Що всередині | M1: що з ним робимо |
|---|---|---|---|
| `kv-network` | `infra/network.yaml` | VPC, підмережі, IGW, route tables, Outputs з ID | деплоїмо |
| `kv-iam` | `infra/iam-readonly.yaml` | read-only політика, роль з trust policy | `validate-template` + policy simulator; одна спроба деплою лише щоб зафіксувати реальну помилку пісочниці, після неї — видалити невдалий стек |
| `kv-app-…` | з M2 | coordinator, шарди | M2 |

**Як стеки пов'язані:** `kv-network` публікує ID VPC і підмереж як **Outputs з Export** (наприклад, `kv-network-VpcId`). Стеки M2 беруть їх через `Fn::ImportValue`. CloudFormation сам стежить за зв'язком: не дасть видалити `kv-network` або змінити експортоване значення, поки хтось його імпортує.

**Порядок:** підняти — `kv-network` → стеки застосунку; знести — у зворотному порядку.

## Чому (докладно)

1. **Інакше M1 не задеплоїти.** В одному стеку IAM-ресурс з AccessDenied відкотить і мережу (атомарність стека). Окремий `kv-network` від IAM не залежить.
2. **Blast radius.** Мережа — фундамент: якщо вона зламається, лягає все. Розділивши стеки, ми гарантуємо, що оновлення застосунку (часто, автоматично з CI/CD) фізично не може змінити VPC.
3. **Різний життєвий цикл.** Мережа створюється раз і живе весь курс; застосунок перевикатується щодня. Ресурси з різним ритмом змін — у різних стеках.
4. **Export/ImportValue, а не ручне копіювання ID.** ID підмереж змінюються після кожного перестворення (завдання 8). Імпорт за назвою експорту завжди бере актуальні значення; а захист від видалення не дасть знести мережу «з-під» застосунку.

## Consequences

**Отримуємо:**
- мережа деплоїться в пісочниці, IAM перевіряється окремо;
- оновлення застосунку не зачіпають мережу;
- ID мережі доступні M2 без ручної роботи.

**Платимо:**
- кілька шаблонів і команд замість одної;
- **жорсткий зв'язок через Export:** поки стек M2 імпортує значення, змінити/видалити його в `kv-network` не можна — спершу треба оновити або видалити стек-споживач;
- порядок видалення має значення (для завдання 8 — у зворотному порядку).

**Що відкинули і чому:**
- **A (один стек)** — не деплоїться в пісочниці через IAM, великий blast radius.
- **C (nested stacks)** — додатковий S3-бакет і шар абстракції, а проблема з IAM лишається.

## Де це в коді

- `infra/network.yaml` → стек `kv-network`.
- `infra/iam-readonly.yaml` → стек `kv-iam` (лише валідація).
- Деплой мережі: `aws cloudformation deploy --template-file infra/network.yaml --stack-name kv-network --profile kse-lab`.
- Перевірка IAM: `aws cloudformation validate-template --template-body file://infra/iam-readonly.yaml --profile kse-lab`.
