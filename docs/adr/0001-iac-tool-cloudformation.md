# ADR-001: IaC-інструмент — AWS CloudFormation

- **Status:** Accepted
- **Date:** 2026-10-31
- **Milestone:** M1 (обов'язковий ADR «Choice of IaC tool»)

## Context

Уся інфраструктура капстоуну (мережа в M1, сервіси в M2–M5) має описуватися кодом (IaC), а не створюватися кліками в консолі. Обмеження, які впливають на вибір:

- **Середовище — AWS Academy Cloud Architecting Sandbox.** Сесії по ~3 год, бюджет **$20** на весь курс, є кнопка Reset. Ключі доступу тимчасові й міняються щосесії. Тому інфраструктура має швидко й надійно підніматися з нуля (завдання 8 M1: знести все і підняти з IaC).
- **Лише AWS.** Інших хмар у проєкті нема й не буде.
- **CI/CD з M2.** Пайплайн у GitHub Actions деплоїтиме інфраструктуру з чужого сервера, а не з мого Mac.
- **Курс.** Лекція 2.1 «IaC. CFN»; контрольне питання 9 M1 — про **change sets** і **drift detection** (терміни CloudFormation).
- **Пісочниця дозволяє** `cloudformation:*` (Readme пісочниці).

## Options

### A) AWS CloudFormation (CFN)
Сервіс самого AWS. Пишемо шаблон (YAML), AWS створює з нього **стек** — групу ресурсів — і **сам на своїй стороні** зберігає, які ресурси в стеку.
- Зміни: **change set** — попередній перегляд «що створиться / зміниться / видалиться» перед застосуванням.
- Ручні зміни в консолі: **drift detection** — AWS порівнює реальні ресурси з шаблоном.
- Видалення стека видаляє всі його ресурси.
- Нічого не треба встановлювати: працює через `aws cloudformation ...`.

### B) Terraform (HashiCorp)
Окрема програма, працює з будь-якою хмарою, мова HCL. Програма сама викликає AWS API і веде **state-файл** `terraform.tfstate` — «записник» відповідностей «`aws_vpc.main` у коді = `vpc-0abc123` в AWS». AWS про цей файл нічого не знає.
- Зміни: `terraform plan` (аналог change set), `terraform apply`.

### C) AWS CDK
Інфраструктура пишеться звичайною мовою програмування (TypeScript/Python), а CDK перетворює її на CloudFormation. Потужно, але додає ще один шар (код → згенерований шаблон → стек). Для мережі з кількох ресурсів це надмірно, і на захисті доводилося б пояснювати обидва шари.

## Decision

**Обираємо A — AWS CloudFormation, шаблони в YAML.**

## Чому (докладно)

**1. Стан зберігає AWS, а не я.** Найважливіша різниця. У Terraform state-файл треба десь зберігати, і з ним пов'язані ризики:
- **state загубився** (видалила папку, працюю з іншого комп'ютера) → Terraform «думає», що нічого не існує, і **створює дублікати**. Старі ресурси лишаються «сиротами», про які ніхто не знає, і вони тратять бюджет $20;
- **CI/CD (M2):** GitHub Actions запускається на чужому сервері, де мого state нема. Тому state кладуть у **S3-бакет** (сховище файлів в AWS) з **блокуванням**, щоб два запуски одночасно не зіпсували файл;
- **«курка і яйце»:** цей бакет треба створити **до** Terraform: руками або окремим bootstrap-кодом;
- **завдання 8 (знести все і підняти):** якщо разом з усім видалити бакет зі state або ключі пісочниці закінчаться посеред `apply`, state залишиться напівзаписаним і його лагодять руками (`terraform import`, `terraform state rm`).

У CloudFormation цього класу проблем нема: стан стека живе в самому AWS. Хоч з Mac, хоч з GitHub Actions, хоч з іншого ноутбука — команда звертається до AWS, і AWS знає, що в стеку.

**2. Відповідає курсу.** Лекція 2.1 — про CFN. Контрольне питання 9 (change sets і drift detection) можна показати наживо на власному стеку.

**3. Нічого не встановлювати й не підтримувати.** Працює через `aws`, який уже є.

**4. Мультихмарність не потрібна.** Головна перевага Terraform (будь-яка хмара) нам нічого не дає: проєкт лише в AWS.

## Consequences

**Отримуємо:**
- немає state-файлу, який можна загубити або зламати;
- простий деплой з будь-якого місця (Mac, CI);
- change sets і drift detection «з коробки»;
- `aws cloudformation validate-template` перевіряє шаблон без деплою: це важливо для IAM-шаблонів (завдання 2–3), які пісочниця задеплоїти не дасть.

**Платимо:**
- **YAML-шаблони багатослівні**, логіки (цикли, умови) мало: для кількох однакових підмереж частину доведеться писати повторно;
- **прив'язка до AWS**: перенести в іншу хмару не вийде (нам і не треба);
- **повільніший цикл**: деякі помилки видно лише під час деплою, а невдалий стек відкочується (`ROLLBACK`), і це забирає час;
- навичка Terraform, популярна на ринку, цим проєктом не прокачується.

**Що відкинули і чому:**
- **Terraform** — через керування state (S3 + lock + bootstrap) у середовищі з тимчасовими ключами і завданням «знести все»; мультихмарність не потрібна.
- **CDK** — зайвий шар абстракції для малої інфраструктури M1.

## Де це в коді

- `infra/` — CloudFormation-шаблони (з'являться після OpenSpec proposal і решти ADR M1).
- Деплой: `aws cloudformation deploy --template-file ... --stack-name ... --profile kse-lab`.
