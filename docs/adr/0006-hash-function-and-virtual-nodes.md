# ADR-006: Хеш-функція MD5 і 500 virtual nodes на шард

- **Status:** Accepted
- **Date:** 2026-11-05
- **Milestone:** M2 (обов'язковий ADR «Hash function and number of virtual nodes»)

## Context

Coordinator обирає шард через consistent hashing: ключ і шарди ставляться на кільце за хешем; ключ належить першій мітці шарда за годинниковою стрілкою. Треба обрати:
1. **хеш-функцію**, що ставить ключі й мітки на кільце;
2. **кількість virtual nodes** (міток) на шард.

Вимоги до хеш-функції для шардингу:
1. **детермінованість** — однаковий результат на будь-якому сервері, в будь-якому процесі, будь-якою мовою;
2. **рівномірність**;
3. **лавинний ефект** — схожі ключі (`user42`, `user43`) далеко один від одного;
4. **широкий діапазон** — мітки майже не збігаються;
5. **є в стандартній бібліотеці Python** (ADR-008).

Криптографічна стійкість **не потрібна**.

## Options

### Хеш-функція
| Функція | Стандартна бібліотека | Прецедент | Коментар |
|---|---|---|---|
| вбудований `hash()` | так | — | ❌ для рядків змінюється між процесами (`PYTHONHASHSEED`) — не детермінована |
| MD5 | `hashlib` | ketama (memcached) | криптографічно «зламана», для розподілу годиться |
| SHA-256 | `hashlib` | — | повільніша, переваг для розподілу нема |
| BLAKE2b | `hashlib` | — | сучасна, швидка |
| MurmurHash3, xxHash | ❌ сторонні пакети | Cassandra, Kafka | без інтернету на сервер не поставити |

### Кількість virtual nodes
1, 10, 50, 100, 200, 500 на шард.

## Експеримент

[`scripts/experiments/ring_distribution.py`](../../scripts/experiments/ring_distribution.py), вивід: [`docs/m2/evidence/ring-distribution.md`](../m2/evidence/ring-distribution.md).

- 1 000 000 ключів `usertable#user<i>` (формат YCSB);
- позиція на кільці = перші 8 байт хешу (0…2⁶⁴);
- кожна комбінація — 20 повторів з різними іменами шардів (одне кільце — один «кидок кубика»);
- **баланс** — відхилення частки shard-1 від 50 % (2 шарди);
- **переїзд** — частка ключів, що міняють шард при додаванні 3-го (ідеал 33,3 %).

| vnodes | баланс: середнє | баланс: найгірше | переїзд 2→3: середнє | переїзд: найгірше відхилення |
|---|---|---|---|---|
| 1 | ≈ 28 pp | ≈ 48 pp | 38–45 % | ≈ 50 pp |
| 10 | 8–10 pp | 17–31 pp | ≈ 33 % | ≈ 15 pp |
| 50 | 4–5 pp | 11–14 pp | ≈ 33 % | 6–9 pp |
| 100 | 2–3 pp | 6–8 pp | ≈ 33 % | 6–8 pp |
| 200 | ≈ 1,7 pp | 4,5–6,7 pp | ≈ 33 % | 5–7 pp |
| 500 | 1,1–1,5 pp | 2,9–3,9 pp | ≈ 33,7 % | 3–4 pp |

Без кільця (`md5 % N`) при 2→3 переїжджає **66,6 %** ключів. Вбудований `hash()` того самого ключа в 3 процесах дав 3 різні числа.

**Висновки експерименту:**
- MD5, SHA-256 і BLAKE2b розподіляють однаково (різниця в межах випадковості) — вибір функції визначають інші критерії;
- кількість virtual nodes визначає рівномірність;
- кільце майже точно реалізує обіцянку «переїжджає ≈ 1/N ключів».

## Decision

**MD5, 500 virtual nodes на шард.**

- Позиція = `int.from_bytes(md5(text.encode("utf-8")).digest()[:8], "big")`.
- Мітки шарда: `"{shard_id}#{i}"`, `i = 0…499`. `shard_id` стабільний (`shard-1`, `shard-2`), **не IP**: IP змінюється після перестворення, а мітки мусять лишатися на місці (ADR-009).
- Ключ на кільці: `"{table}#{partition key}"` (ADR-007).
- Пошук: двійковий пошук першої мітки, більшої за позицію ключа; якщо таких нема — перша мітка кільця.

## Чому (докладно)

1. **MD5 серед рівних за розподілом** — в стандартній бібліотеці будь-якої мови, класичний прецедент (ketama). «Зламаний» лише для безпеки (колізії можна підібрати навмисно), що для розподілу ключів не важливо: клієнт і так сам обирає свої ключі.
2. **500 vnodes:** у найгіршому з 20 повторів ≈ 54/46; 200 — до 57/43. Ціна 500 мізерна: 2 × 500 = 1000 чисел у пам'яті, пошук ≈ 10 порівнянь. У M5 (більше шардів) — кілька тисяч чисел, теж дрібниця.
3. **Детермінованість перевірено** експериментом (вбудований `hash()` — ні).

## Consequences

**Отримуємо:**
- розподіл 50 ± ~1,5 pp у середньому;
- додавання шарда переносить ≈ 1/N ключів (основа для ребалансу в M5).

**Платимо:**
- на захисті треба пояснити «чому MD5, він же зламаний» (відповідь вище);
- MD5 повільніша за некриптографічні функції — у мікросекундах, на тлі мілісекунд мережі не видно;
- рівномірність **ключів**, а не **навантаження**: гарячий ключ усе одно б'є в один шард (ADR-007).

**Що відкинули і чому:**
- **`hash()`** — не детермінований між процесами.
- **MurmurHash3 / xxHash** — сторонні пакети на сервері.
- **SHA-256 / BLAKE2b** — рівні за розподілом, але без переваг над MD5 для нашої задачі.
- **≤ 100 vnodes** — у найгіршому з 20 повторів на одному шарді 58 % (100 vnodes), 81 % (10) і до 98 % (1).

## Де це в коді

- Модуль кільця (coordinator) + тести: детермінованість, баланс, переїзд ≈ 1/N.
- Експеримент: `scripts/experiments/ring_distribution.py`.
