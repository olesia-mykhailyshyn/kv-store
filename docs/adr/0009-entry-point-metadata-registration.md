# ADR-009: Точка входу, метадані coordinator і реєстрація шардів

- **Status:** Accepted
- **Date:** 2026-11-05
- **Milestone:** M2 (додатковий ADR)

## Context

1. **Точка входу.** Coordinator у приватній підмережі (ADR-008), без публічної IP. API Gateway у пісочниці нема. Як клієнт (YCSB, `curl`) до нього дістається?
2. **Метадані.** Coordinator пам'ятає визначення таблиць і кільце. Що буде після його перезапуску?
3. **Реєстрація шардів** (M2, завдання 3): шарди реєструються в coordinator при старті. IP шардів змінюються після кожного перестворення стека.
4. **Доставка коду** на сервери без інтернету.

Перевірено в пісочниці 2026-11-05 (`--dry-run`, читання IAM, симулятор; журнал M2, крок 28): key pair, S3 Gateway Endpoint, EC2 Instance Connect, створення бакета — дозволені; `myS3Role` має доступ до S3.

## Options

### Точка входу
| | 1. Клієнт у VPC | 2. ALB | 3. Публічна IP coordinator |
|---|---|---|---|
| Як | EC2-клієнт у публічній підмережі → приватна IP coordinator | публічний ALB → coordinator | coordinator у публічній підмережі |
| Ціна, 40 год | $0 зверху | +$1.62 | +$0.20 |
| `curl` з Mac | ні, з клієнта | так | так |
| Ізоляція coordinator | повна | через ALB | ❌ відкритий в інтернет |
| Зайвий вузол у вимірюванні latency | ні | так | ні |

### Метадані
лише RAM; RAM + WAL на EBS coordinator; зовнішнє сховище (S3 / DynamoDB).

## Decision

**Точка входу — 1, клієнт у VPC.**
- На клієнт заходимо через SSH (key pair) або EC2 Instance Connect.
- `curl` для демо і YCSB запускаються на клієнті.

**Security groups (найменші дозволи):**

| Від | До | Порт |
|---|---|---|
| клієнт SG | coordinator SG | API (8080) |
| coordinator SG | shard SG | API шарда (8080) |
| shard SG | coordinator SG | 8080 (реєстрація) |
| Mac (IP Олесі) / діапазон EC2 Instance Connect | клієнт SG | 22 |

Більше ніякого вхідного трафіку.

**Метадані — RAM + WAL на EBS coordinator** (той самий механізм, що в шардах, ADR-008):
- визначення таблиць переживають перезапуск coordinator;
- кільце в WAL **не** пишемо — його відновлює реєстрація.

**Реєстрація — heartbeat:**
- Шард одразу після старту і далі **кожні 5 с** надсилає `POST /shards/register {"id":"shard-1","url":"http://<private-ip>:8080"}`.
- `id` — стабільний, задається в IaC (`shard-1`, `shard-2`), **не** IP. Мітки на кільці залежать від `id`, тож після перестворення сервера ключі лишаються «на своєму» шарді.
- Новий `id` → додається на кільце. Відомий `id` з новою адресою → адреса оновлюється.
- Адресу coordinator шард отримує з user data (CloudFormation `!GetAtt Coordinator.PrivateIp`).
- Шард, що замовк, у M2 **з кільця не прибираємо** (це перемістило б ключі); запити до нього → `503`. Виявлення відмов і ребаланс — M5.

**Доставка коду:** архів у бакет S3 → сервер у user data забирає його через **S3 Gateway Endpoint** ($0), додаємо його до `kv-network`.

## Чому (докладно)

1. **Клієнт у VPC** — безкоштовно, coordinator не виставлений в інтернет (модель M1), YCSB міряє сховище без проміжного вузла.
2. **WAL для метаданих** — повторне використання коду шарда; без нього після перезапуску coordinator таблиці «зникли» б, хоча дані на шардах є.
3. **Heartbeat замість одноразової реєстрації** — кільце саме збирається після перезапуску coordinator; основа для health-check у M5.
4. **Стабільний `id`** — інакше нова IP = нові мітки = ключі «переїхали» без переносу даних.
5. **Gateway Endpoint замість NAT** — $0 проти ≈ $5.40 за 40 год (3 NAT).

## Consequences

**Отримуємо:**
- закритий від інтернету coordinator і шарди;
- самовідновлюване кільце;
- доставку коду без NAT.

**Платимо:**
- демо через клієнт, не з Mac;
- після перезапуску coordinator до 5 с запити отримують `503`, доки шарди не зареєструються;
- **реєстрація без автентифікації:** будь-хто з доступом до coordinator SG може зареєструвати «шард». Захист у M2 — лише security groups;
- **зміна `kv-network`** (Gateway Endpoint + маршрут у приватних route tables) — оновлення M1-шаблону і його перевірок;
- ALB не використовуємо — він лишається шляхом масштабування coordinator (ADR-008).

**Що відкинули і чому:**
- **ALB** — +$1.62 і зайвий вузол у latency; у M2 не потрібен.
- **Публічна IP coordinator** — ламає ізоляцію з M1.
- **Метадані лише в RAM** — втрачаються таблиці.
- **Зовнішнє сховище метаданих** — потрібне лише для кількох coordinator.

## Де це в коді

- `infra/network.yaml` — S3 Gateway Endpoint.
- `infra/app.yaml` — EC2, security groups, user data (адреса coordinator, `id` шарда, завантаження коду з S3).
- Шард: heartbeat-цикл. Coordinator: `POST /shards/register`, WAL метаданих.

## Поправка (2026-11-06, після code review M2)

**Проблема:** «захист лише security groups» не працює для реєстрації. API і `/shards/register` слухають той самий порт 8080, а на нього за SG ходить і клієнт. Будь-хто з доступом до coordinator міг би:
- зареєструвати фальшивий шард (≈ 1/3 ключів → `503` назавжди, бо в M2 шарди не прибираються);
- підмінити адресу `shard-1`, наприклад на `169.254.169.254` (сервіс метаданих EC2).

**Рішення:** coordinator приймає реєстрацію, лише якщо **host у `url` дорівнює IP, з якого прийшов запит**. Шард може зареєструвати тільки власну адресу.
Тест: `test_register_rejects_url_of_another_host`.

**Залишковий ризик:** клієнт у VPC усе ще може зареєструвати **себе** як шард з новим `id`. Повний захист — спільний секрет (токен шарда) або окремий внутрішній порт для реєстрації; відкладено до M5, де реєстрація стане частиною автомасштабування.
