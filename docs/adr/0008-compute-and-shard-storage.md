# ADR-008: Compute і зберігання — усе на EC2, Python stdlib, RAM + WAL на EBS

- **Status:** Accepted
- **Date:** 2026-11-05
- **Milestone:** M2 (додатковий ADR)

## Context

Треба вирішити:
1. **на чому працюють** coordinator і шарди: EC2 чи Lambda;
2. **якою мовою** вони написані;
3. **як шард зберігає записи**.

Обмеження й факти:
- **Шард stateful** (його робота — тримати дані), coordinator майже stateless (кільце відновлюється).
- **Лекція 9:** «ваші шарди живуть на EBS»; типова пастка — тримати дані шарда в `/tmp` Lambda (зникають при recycle середовища). Coordinator як Lambda — приклад, не вимога.
- **Пісочниця:** ≤ 9 EC2, `t2/t3` до `medium`; приватні підмережі без NAT → на сервері нема інтернету (`pip install` не працює).
- **Бюджет M2** ([`docs/m1/budget-m2.md`](../m1/budget-m2.md), 40 год сесій): усе EC2 — $2.66; Lambda + DynamoDB — $5.38; змішаний — $3.41.
- **M3** вимагає «leader + log, followers with offsets».

## Options

### Compute
| | А. Усе EC2 | Б. Lambda + DynamoDB | В. Coordinator Lambda, шарди EC2 |
|---|---|---|---|
| Власний шардинг | ✅ | ❌ шардинг робить DynamoDB | ✅ |
| Реєстрація шарда при старті | природна | штучна (Lambda не «стартує») | природна, але кільце — у зовнішньому сховищі з перечитуванням за версією |
| Coordinator bottleneck | так | ні | ні |
| YCSB baseline | без cold start | cold start | cold start coordinator |
| Неперевірені ризики | — | Function URL | права Lambda на ENI у VPC, Function URL |
| Вартість, 40 год | **$2.66** | $5.38 | $3.41 |
| EC2 у M3 (ліміт 9) | 8 | — | 7 |

### Мова
Python (є в Amazon Linux 2023, HTTP-сервер у stdlib), TypeScript/Node (треба ставити Node), Go (один бінарник, але нова мова), Java (важка для 1 ГБ RAM).

### Зберігання шарда
1. лише RAM; 2. **RAM + append-only WAL на EBS**; 3. SQLite на EBS; 4. RocksDB/LevelDB.

## Decision

**Compute — А, усе на EC2:**

| Роль | Тип | Підмережа | Кількість |
|---|---|---|---|
| coordinator | `t3.micro` | приватна | 1 |
| шард | `t3.micro`, EBS `gp2` 8 ГБ | приватні, **різні AZ** | 2 |
| клієнт (YCSB, `curl`) | `t3.small` | публічна | 1 |

Разом **4 EC2 з 9**. Роль серверів — готова `myS3Role` (instance profile є; перевірено 2026-11-05).

**Мова — Python 3, лише стандартна бібліотека на серверах:** `http.server` (`ThreadingHTTPServer`), `json`, `hashlib`, `urllib.request`. Залежності (валідатор OpenAPI, тести) — лише в CI.

**Зберігання шарда — RAM + WAL (write-ahead log) на EBS:**
- **Запис:** рядок у `wal.log` → `fsync` → оновити RAM → відповідь `201`. Відповідь «збережено» = дані вже на диску.
- **Формат рядка:** JSON Lines `{"op":"put|delete","table":…,"pk":…,"sk":…,"value":…}`.
- **Читання:** з RAM.
- **Старт:** програти `wal.log` з початку → відновлений стан.
- **У RAM:** записи згруповані за `(table, pk)` → `{sk: value}`; для Query — сортування за SK.
- **fsync на кожен запис** у M2. Групування (group commit) — лише якщо YCSB покаже, що fsync — вузьке місце.
- **Compaction** — не в M2 (журнал за сесію не встигає вирости).

## Чому (докладно)

1. **Шард stateful → EC2 + EBS.** Lambda не може тримати дані сама; Б перекладає шардинг на DynamoDB, а оцінюється наш шардинг (★DS-2).
2. **А простіше за В** — без Lambda у VPC, без зовнішнього сховища кільця, без cold start у baseline; найдешевше; без неперевірених прав.
3. **Python stdlib** — нічого не ставимо на сервер без інтернету; Олеся пояснює кожен рядок.
4. **WAL:**
   - кожен рядок пояснюється (касова стрічка: дописуємо в кінець, нічого не стираємо);
   - append-only безпечний при падінні — пошкодитися може лише останній рядок;
   - **той самий журнал — лог реплікації M3** (offset = номер запису).
5. **fsync на кожен запис** — найпростіша гарантія «201 = на диску». Чесно платимо latency; YCSB покаже ціну.

## Consequences

**Отримуємо:**
- власний шардинг на справжніх серверах з диском;
- чистий YCSB baseline;
- фундамент для реплікації M3.

**Платимо:**
- **один coordinator — bottleneck і single point of failure.** Масштабування (не в M2): кілька coordinator за ALB зі спільними метаданими, або coordinator у Lambda (варіант В). Відповідь на контрольне питання 7;
- **усі дані шарда мусять уміщатися в RAM** (`t3.micro` ≈ 1 ГБ; YCSB 100 000 × 1 КБ ≈ 100 МБ — вистачає);
- **fsync на кожен запис** — вищий latency записів;
- `t3` — burstable: під тривалим навантаженням CPU credits вичерпуються, і продуктивність падає до базової. Враховуємо при читанні YCSB;
- **`myS3Role` має `s3:*` на всі бакети** — ширше, ніж треба (least privilege порушено). Змінити не можемо (IAM лише на читання) — свідомий ризик пісочниці;
- дані живуть лише в межах сесії лаби (платформа видаляє стеки разом з EBS) — YCSB завантажує їх щоразу.

**Що відкинули і чому:**
- **Б (Lambda + DynamoDB)** — шардинг робить AWS, реєстрація штучна, найдорожче в сесіях.
- **В (змішаний)** — складніше; права Lambda у VPC не перевірені; cold start у baseline. Лишається шляхом масштабування coordinator.
- **Лише RAM** — перезапуск = втрата даних.
- **SQLite** — «чорна скринька»; для M3 однаково потрібен окремий лог.
- **RocksDB/LevelDB** — сторонній пакет, нутрощі важко пояснити.

## Поправка (2026-11-06, після code review M2)

**Відоме обмеження WAL:** якщо `write` або `fsync` падає посеред запису (наприклад, диск заповнений), у кінці файлу може лишитися частина рядка без `\n`. Наступний запис допишеться до неї, і зламаний рядок опиниться **посередині** файлу. Тоді наступний старт відмовиться працювати (`WalCorruptedError`).
- **Чому це прийнятно в M2:** клієнт у цьому випадку отримав помилку (`500`), а не `201`, тож жодне підтверджене значення не губиться. Шард просто не стартує, доки людина не обріже файл.
- **Як закрити (M3, разом з логом реплікації):** після помилки запису обрізати файл до останнього повного рядка або писати кожен запис з довжиною і контрольною сумою.

**Знахідка під час інтеграції (Nagle):** `http.server` надсилає заголовки й тіло двома записами. Алгоритм Nagle затримував тіло до ACK заголовків, а клієнт відкладає ACK на ~40 мс, тож кожен запит на keep-alive з'єднанні тривав ~45 мс. Виправлено `disable_nagle_algorithm = True` (TCP_NODELAY). Локальний YCSB (Docker): 176 → 2548 ops/s.
