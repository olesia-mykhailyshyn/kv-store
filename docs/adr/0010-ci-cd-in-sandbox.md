# ADR-010: CI/CD у пісочниці — CI на кожен push, CD кнопкою з ключами сесії в GitHub Secrets

- **Status:** Accepted
- **Date:** 2026-11-05
- **Milestone:** M2 (додатковий ADR; навичка INF-2)

## Context

M2, завдання 5: CI/CD pipeline, що деплоїть **і інфраструктуру, і застосунок**.

Обмеження пісочниці:
- **OIDC неможливий:** `iam:CreateOpenIDConnectProvider` = implicitDeny (симулятор, [`docs/m1/ai-critique.md`](../m1/ai-critique.md)); ролі створювати не можна. GitHub не отримає тимчасовий доступ без збережених ключів.
- **Ключі сесії живуть ~3 год** і змінюються щосесії.
- **Наприкінці сесії платформа видаляє стеки** — кожна сесія починається з порожнього акаунта.
- **Coordinator у приватній підмережі** — комп'ютер GitHub до нього не дістанеться.

## Options

### 1. CI на кожен push + CD кнопкою, ключі сесії в GitHub Secrets
- ➕ Pipeline справді деплоїть infra й app.
- ➕ CI працює завжди, навіть без лаби.
- ➖ Щосесії одна ручна команда для оновлення ключів.

### 2. Лише CI, деплой скриптом з Mac
- ➕ Найпростіше.
- ➖ Вимогу «pipeline деплоїть» по суті не виконано.

### 3. Self-hosted runner на EC2 у пісочниці
- ➕ Без ключів у GitHub (права з ролі сервера).
- ➖ `myS3Role` має лише S3 — без CloudFormation/EC2.
- ➖ Runner реєструвати щосесії; ще 1 EC2 з 9.

## Decision

**Обираємо 1.**

**CI** — GitHub Actions, на кожен push і pull request, **без AWS**:
1. тести Python (кільце, WAL, coordinator, шард);
2. перевірка коду на відповідність `api/openapi.yaml`;
3. `cfn-lint` для шаблонів;
4. валідація `api/openapi.yaml`.

**CD** — окремий workflow, `workflow_dispatch` (кнопка «Run workflow»):
1. `aws cloudformation deploy` → `kv-network` (немає змін → «No changes»);
2. архів коду → бакет S3 (бакет — в окремому стеку, щоб існував до `kv-app`);
3. `aws cloudformation deploy` → `kv-app` з версією коду як параметром;
4. **smoke test зсередини VPC** (`PUT` → `GET` → `DELETE` → `/health`); механізм — у design;
5. pipeline червоний, якщо будь-який крок упав.

**Ключі:**
- секрети `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_SESSION_TOKEN`;
- на старті сесії: `gh secret set …` з Mac (значення читаються з `lab-credentials.ini`, у чат і код не потрапляють);
- GitHub маскує секрети в логах;
- `workflow_dispatch` запускає лише власниця репозиторію; pull request з форків секретів не отримують.

**Для CD не використовуємо** `recreate-network.sh` — він видаляє мережу.

## Чому (докладно)

1. **Єдиний варіант, що чесно виконує вимогу** в пісочниці без OIDC.
2. **CI окремо від CD:** перевірки не потребують AWS і ловлять помилки до деплою, навіть коли лаба вимкнена.
3. **Кнопка, а не автодеплой на push:** без активної сесії ключі недійсні, автодеплой падав би на кожен push.
4. **`cloudformation deploy` ідемпотентний** — повторний запуск безпечний.
5. **Smoke test у pipeline:** «стек створено» ≠ «програма працює».

## Consequences

**Отримуємо:**
- автоматичні перевірки кожної зміни;
- деплой infra + app однією кнопкою;
- червоний pipeline при зламаному деплої.

**Платимо:**
- ручне `gh secret set` щосесії (обмеження пісочниці, не вибір);
- ключі сесії в GitHub Secrets мають усі права `voclabs` на час сесії — ризик обмежений ~3 год і пісочницею;
- smoke test потребує механізму всередині VPC (design).

**Що відкинули і чому:**
- **Лише CI** — не виконує вимогу.
- **Self-hosted runner** — роль без потрібних прав, ще 1 EC2, реєстрація щосесії.
- **OIDC** — заборонено в пісочниці; правильний вибір поза нею.

## Де це в коді

- `.github/workflows/ci.yml`, `.github/workflows/deploy.yml`.
- `scripts/` — скрипт оновлення секретів з `lab-credentials.ini`.
