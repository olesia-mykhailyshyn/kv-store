## 2. Як ми працювали: spec before code

Правило курсу: спершу специфікація й рішення, потім код. Писати специфікацію після коду вважається порушенням академічної доброчесності.

```
proposal → specs + design → tasks → код → перевірка → archive
```

| Документ | Питання | Що далі |
|---|---|---|
| `proposal.md` | навіщо і що робимо | в архів |
| `specs/` | що система мусить робити | у `openspec/specs/`, живе далі |
| `design.md` | як робимо | в архів |
| `tasks.md` | які кроки | в архів |
| ADR | чому обрали саме так | лишається назавжди |

Прийнятий ADR не переписують, а додають поправку. Так і зроблено після AI-критики.

**Доказ порядку:** коміт специфікації в git стоїть раніше за коміт із шаблоном мережі.

## 3. IaC і CloudFormation

- **Шаблон** — файл із описом бажаного результату, «бланк замовлення». Сам нічого не створює.
- **Ресурс** — одна конкретна річ в AWS: VPC, підмережа, маршрут.
- **Стек** — група ресурсів, створена з одного шаблону. CloudFormation пам'ятає, що в неї входить.

**Як CloudFormation створює ресурси:**
1. Отримує шаблон.
2. Будує залежності з `!Ref` і `DependsOn`.
3. Викликає API сервісів **з нашими правами**. Незалежні ресурси створює паралельно.
4. Запам'ятовує, який реальний ID отримав кожен ресурс.
5. При помилці робить rollback: прибирає все створене.

**Чому CloudFormation, а не Terraform (ADR-001):** стан зберігає сам AWS, тож немає state-файлу, який можна загубити; нічого не треба встановлювати; курс побудований на CFN; мультихмарність не потрібна.

**Чому мережа й IAM окремо (ADR-002):** стек працює за принципом «усе або нічого», тому IAM-ресурс, заборонений у пісочниці, відкотив би й мережу.

**Елементи шаблону:**

| Елемент | Що робить |
|---|---|
| `Parameters` | поля, які заповнюють під час деплою |
| `Resources` | що створити, обов'язковий розділ |
| `Outputs` / `Export` | що показати назовні, значення для інших стеків |
| `!Ref` | ID ресурсу або значення параметра |
| `!GetAtt` | інша властивість ресурсу |
| `!Sub` | підстановка в текст |
| `!Select` + `!GetAZs` | взяти AZ зі списку регіону |
| `DependsOn` | явний порядок створення |

## 4. Мережа

```
                 Інтернет
                    │
                  [IGW]
   ┌────── VPC 10.0.0.0/16 ──────┐
   │ AZ 1: public-a   private-a  │
   │ AZ 2: public-b   private-b  │
   │ AZ 3: public-c   private-c  │
   └─────────────────────────────┘
```

| Частина | Аналогія | Навіщо |
|---|---|---|
| **VPC** | ЖК з парканом | ізольована мережа |
| **Підмережа** | будинок | частина мережі в одній AZ |
| **IGW** | ворота | вихід в інтернет |
| **Route table** | вказівники на виході | куди везти пакет |
| **Прив'язка** | записка «який аркуш у вас діє» | зв'язує підмережу з таблицею |

**Публічною підмережу робить маршрут `0.0.0.0/0 → IGW`.** Таблиць 2, бо правил лише два набори. Прив'язок 6, бо в AWS це окремий ресурс на кожну підмережу.

**Рішення (ADR-003):**
- **`/16`:** адреси безкоштовні, а змінити діапазон потім не можна. Це запас, а не потреба.
- **`/24`:** зручно читати, третє число позначає підмережу.
- **3 AZ:** для кворуму в M3.
- **Без NAT:** приблизно $33 на місяць за один, а в M1 не потрібен.

**NAT чи S3 Gateway Endpoint.** NAT дає приватним серверам вихід в увесь інтернет за гроші. Gateway Endpoint — безкоштовний тунель лише до S3 або DynamoDB. Розглядаємо його для доставки коду в M2, але рішення ще не прийняте.

## 5. IAM

| Поняття | Простими словами |
|---|---|
| **Principal** | той, від чийого імені йде запит |
| **Policy** | аркуш правил: `Effect`, `Action`, `Resource`, `Condition` |
| **Role** | картка-перепустка без пароля, яку беруть на час |
| **Trust policy** | кому можна видати картку |
| **Permissions policy** | куди з карткою пускають |
| **Сесія** | один конкретний раз, коли роль узяли; ключі тимчасові |

**Наша роль `kv-readonly`:**
- **Хто:** аудитор з іншого акаунта, лише з MFA, сесія до 1 години.
- **Що:** Allow на перегляд (49 дій) + explicit Deny на дані й секрети (25 дій).

**Чому своя політика, а не `ReadOnlyAccess`:** та дозволяє читати дані (`s3:Get*`, `dynamodb:Scan`). «Перегляд» у нас означає лише метадані.

**Що ми зрозуміли:**
- Назва дії не гарантує безпеку: деякі `Describe` і `Get` віддають секрети.
- Зірочка в Allow ризикована. У Deny вона безпечна, а `Resource: "*"` потрібен для дій перегляду.
- Deny закриває лише названі дії.
- `ListFunctions` і `GetTemplate` лишили свідомо: без них аудитор не бачить функцій і стеків.

**Як перевірили без деплою:** `validate-template` (синтаксис), симулятор (37/37 для логіки політики), читання trust policy.

## 6. Пісочниця: що ми з'ясували

- Працюємо як `voclabs`; `LabRole` немає.
- Обмеження йдуть із трьох шарів: `ReadOnlyAccess`, `Pvoclabs`, SCP. Текст помилки називає джерело заборони.
- Лекція каже, що Organizations у пісочниці немає. Насправді **ми** не можемо її створити, а наш акаунт уже входить в організацію Academy.
- **Наприкінці сесії платформа видаляє стеки.** Знайшли через CloudTrail: `DeleteStack` від ролі `vocareum`.

**Невідомо:** чи так само зникають сервери, диски й непорожні бакети. Це перевіримо в M2.

## 7. Квоти і бюджет

**Квота** — ліміт AWS на акаунт. Квоти для M2 мають великий запас. Реально обмежують **правила пісочниці**: ≤ 9 EC2, малі типи серверів, немає API Gateway, SQS і ECS; а також бюджет $20.

**Бюджет:** ціни взяли з публічних прайсів AWS, бо Pricing API заборонений.

| Варіант | 24/7 | 40 год сесій |
|---|---|---|
| А. EC2 без ALB | $45.01 | $2.66 |
| А+. EC2 + ALB | $74.58 | $4.28 |
| Б. Serverless | $23.94 | $5.38 |
| В. Змішаний | $37.83 | $3.41 |

**Висновок:** 24/7 не вміщається ніщо. У режимі сесій вміщається все, але **ця оцінка оптимістична:** не враховано завантаження даних YCSB, розмір запису й режим `unlimited`, а видалення платних ресурсів не перевірено. Це відкладено на M2. Архітектуру оберемо в M2.

## 8. Відтворюваність

`scripts/recreate-network.sh`: знести → підняти → 11 перевірок → час. Результат: 32 с + 68 с = **100 с**. ID щоразу нові, тому M2 візьме їх через експорти, а не вписаними в код.

Окрема сесія AI отримала факти й файли, але не наше обговорення. Вона знайшла 12 проблем, ми перевірили кожну. Найцінніше: скрипт перевірки міг написати «All checks passed», коли AWS не відповідав.
