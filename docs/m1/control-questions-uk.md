# M1: відповіді на контрольні питання

Шпаргалка для повторення. На захисті нотатки не дозволені, тому мета — вміти сказати це своїми словами. Теорія ширше: [`theory-uk.md`](theory-uk.md).

## 1. *aaS: порівняй хмарні моделі. Коли що використовувати

Моделі відрізняються тим, **за що відповідаєш ти, а за що провайдер**.

| Модель | Що дає провайдер | Що лишається на тобі | Аналогія з лекції 1 | Приклади |
|---|---|---|---|---|
| **IaaS** | сервери, мережа, диски | ОС, рантайм, застосунок, дані | будуєш будинок із цегли | EC2, VPC |
| **PaaS** | ще й платформу для запуску | лише код і дані | збираєш із готових панелей | Lambda, Heroku, ECS |
| **SaaS** | готовий продукт | лише користування й налаштування | орендуєш номер у готелі | Google Docs, Salesforce |

**Коли що:**
- **IaaS:** потрібен повний контроль, особливі вимоги або перенесення наявної системи.
- **PaaS:** важлива швидкість розробки, а керувати серверами не хочеться.
- **SaaS:** задача не є твоєю основною справою, і готове рішення її закриває. Ціна: залежність від постачальника й менше гнучкості.

**У проєкті:** мережа M1 — це IaaS. Для M2 розглядаємо EC2 (IaaS) і Lambda (PaaS).

## 2. Регіони, Availability Zones

- **Регіон** — географічна область із кількома ізольованими групами дата-центрів. Вибір впливає на затримку, юрисдикцію, ціну й доступні сервіси.
- **Availability Zone (AZ)** — один або кілька дата-центрів усередині регіону зі своїм живленням, охолодженням і мережею. AZ одного регіону з'єднані швидкими каналами, а їхні аварії незалежні.
- **Навіщо кілька AZ:** падіння однієї не зупиняє систему.

**У проєкті:** регіон `us-east-1` (6 AZ, перевірено командою). Беремо 3 AZ, щоб у M3 3 репліки стояли в різних зонах: падіння однієї лишає 2 з 3, тож кворум зберігається.

## 3. Що таке IaC і в чому цінність

**IaC (Infrastructure as Code)** — інфраструктура описана текстом у файлах, а не створюється кліками в консолі. CloudFormation декларативний: описуємо бажаний результат, а не кроки.

**Цінність:**
- **Відтворюваність:** підняти те саме можна будь-коли. У нас: 100 с від знесення до готової мережі.
- **Історія:** усі зміни видно в git, їх можна переглянути й повернути.
- **Менше помилок:** жодних забутих ручних кроків.
- **Перегляд перед зміною:** change set показує наслідки.

**У проєкті це необхідність:** пісочниця видаляє наші стеки в кінці кожної сесії.

## 4. Ролі чи групи для призначення політик

| | Група | Роль |
|---|---|---|
| Суть | постійне членство | перевтілення на час сесії |
| Для кого | лише IAM-користувачі | люди, сервіси, інші акаунти |
| Ключі | своїх немає | видає тимчасові |
| Чи є principal | ні | так |
| Між акаунтами | ні | так |

**Групи** зручні, щоб видати однакові права багатьом людям одного акаунта. **Ролі** потрібні для сервісів, доступу з іншого акаунта й тимчасових прав. Лекція 2: людям — Identity Center, машинам — ролі, довгі ключі — нікому.

**У проєкті:** аудитор з іншого акаунта, тому тільки роль.

## 5. VPC, CIDR, обчислення блоків

**VPC** — твоя ізольована мережа в AWS. **CIDR** задає діапазон адрес: число після `/` каже, скільки перших біт зафіксовано.

**Формула: кількість адрес = 2^(32 − N).**

| CIDR | Адрес | Вільних в AWS |
|---|---|---|
| `/16` | 65 536 | — |
| `/20` | 4 096 | 4 091 |
| `/24` | 256 | 251 |
| `/28` | 16 | 11 |

AWS забирає 5 адрес у кожній підмережі: `.0` (мережа), `.1` (роутер), `.2` (DNS), `.3` (резерв) і останню (broadcast).

**У проєкті:** VPC `10.0.0.0/16` і 6 підмереж `/24`. Публічні: `10.0.0–2.0/24`. Приватні: `10.0.10–12.0/24`. Отже, зайнято 1 536 адрес із 65 536.

## 6. Як влаштувати публічні й приватні підмережі. Як це працює

Різницю задає **маршрут**, а не назва:
- **Публічна:** у route table є `0.0.0.0/0 → IGW`.
- **Приватна:** такого маршруту немає. У нас лише `10.0.0.0/16 → local`. За термінами лекції 3.2 це **isolated subnet**, бо немає й NAT.

Щоб до сервера дістатися з інтернету, потрібні всі три умови: маршрут до IGW, публічна IP і security group, що пускає трафік.

AWS обирає **найточніший** маршрут: `10.0.11.5` піде через `local`, `8.8.8.8` — через IGW.

**Навіщо приватні:** шарди й дані не мають бути доступні ззовні. **У проєкті:** 2 таблиці, 6 явних прив'язок; main route table не використовуємо, щоб забута підмережа не стала публічною.

**Чесно:** ми перевірили налаштування (маршрути, прив'язки), а живий трафік не пускали. Він перевіриться в M2.

## 7. Коли allow, а коли deny

Порядок оцінки:
1. За замовчуванням усе заборонено (**implicit deny**).
2. Є **explicit Deny** — заборонено, жоден Allow не перебʼє.
3. Є **Allow** — дозволено.
4. Нічого немає — заборонено.

- **Allow** видає потрібне. Це основний інструмент.
- **Explicit Deny** — запобіжник для того, чого не можна за жодних умов.

**У проєкті:** `kv-readonly` має Allow на перегляд (49 дій) і Deny на дані й секрети (25 дій). Симулятор: разом із чужою політикою `s3:*` дія `s3:GetObject` лишається `explicitDeny`. **Обмеження:** Deny закриває лише названі дії, тому це запобіжник, а не гарантія.

## 8. Що дозволяє і забороняє LabRole? Як ти це з'ясувала

**`LabRole` в нашому акаунті немає**, ми працюємо як сесія ролі **`voclabs`** (`aws sts get-caller-identity`, `iam list-roles`).

**Права складаються з трьох шарів:** `ReadOnlyAccess` (AWS, лише Allow) → `Pvoclabs` (Academy, текст прихований, є Deny) → SCP організації.

**Дозволено:** читати майже все; створювати VPC, стеки, EC2 (≤ 9, `t2/t3` до `medium`), Lambda, DynamoDB, S3; передавати сервісам готові ролі `lambda-run-role`, `myBasicLambdaRole`, `myS3Role`.

**Заборонено:**

| Що | Тип | Текст помилки |
|---|---|---|
| створювати IAM-ролі | implicit deny | `no identity-based policy allows` |
| читати `voclabs` і `Pvoclabs` | explicit deny у ролі | `explicit deny in an identity-based policy` |
| Pricing API, Organizations, деталі ролі `vocareum` | explicit deny від SCP | `explicit deny in a service control policy` |
| API Gateway, SQS | implicit deny | симулятор: `implicitDeny` |

**Як з'ясувала:** Readme пісочниці → CLI → policy simulator (з конкретними ARN, бо заборони залежать від ресурсу) → проби з `--dry-run` → текст помилок → CloudTrail.

Детально: [`role-dissection.md`](role-dissection.md).

## 9. Change sets і drift detection: що показують і коли потрібні

| | Change set | Drift detection |
|---|---|---|
| Коли | **до** зміни | **після** |
| Порівнює | новий шаблон зі стеком | шаблон стека з реальними ресурсами |
| Питання | «що станеться, якщо застосую?» | «чи змінив хтось ресурси в обхід шаблону?» |
| Показує | `Add`, `Modify`, `Remove` | `IN_SYNC`, `MODIFIED`, `DELETED`, `NOT_CHECKED` |

**Обмеження drift detection:** бачить зміни властивостей ресурсів стека, але не ресурси, додані поза ним. Сама нічого не виправляє.

**У проєкті:** change set зробили на практиці (18 × `Add`). Drift detection на практиці **не запускали**, це свідоме рішення: завдання вимагає лише пояснити.
