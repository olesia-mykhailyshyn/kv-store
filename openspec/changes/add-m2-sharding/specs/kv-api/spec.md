# Spec Delta

## Purpose

Публічний контракт kv-сховища: як клієнт створює таблиці й працює з записами за ключем, які коди відповідей і помилки отримує. Контракт однаковий незалежно від того, скільки шардів за ним стоїть.

## ADDED Requirements

### Requirement: Контракт описаний в OpenAPI до коду
Публічне і службове API SHALL бути описане у файлі `api/openapi.yaml` (OpenAPI 3.1, REST + JSON). Специфікацію MUST бути закомічено раніше за код, що її реалізує. Поведінка сервісу MUST відповідати специфікації.

#### Scenario: Специфікація валідна
- **WHEN** запускаємо валідатор OpenAPI на `api/openapi.yaml`
- **THEN** валідатор не повідомляє про помилки

#### Scenario: Специфікація раніше за код
- **WHEN** переглядаємо історію git
- **THEN** коміт з `api/openapi.yaml` передує першому коміту з кодом coordinator

### Requirement: Реєстрація визначення таблиці
Клієнт SHALL створювати таблицю запитом з назвою, ім'ям атрибута partition key і (опційно) ім'ям атрибута sort key. Назва таблиці MUST відповідати `[A-Za-z0-9_-]{1,64}`.

#### Scenario: Нова таблиця зі sort key
- **WHEN** клієнт надсилає `POST /tables` з `{"name":"orders","partitionKey":"userId","sortKey":"orderDate"}`
- **THEN** відповідь `201`, і `GET /tables/orders` повертає це визначення

#### Scenario: Таблиця вже існує
- **WHEN** клієнт повторно створює таблицю з тією самою назвою
- **THEN** відповідь `409`, визначення не змінюється

#### Scenario: Неприпустима назва
- **WHEN** назва таблиці містить `#` або інший символ поза `[A-Za-z0-9_-]`
- **THEN** відповідь `400`

### Requirement: Визначення таблиць переживають перезапуск coordinator
Створені таблиці MUST залишатися доступними після перезапуску процесу coordinator.

#### Scenario: Перезапуск coordinator
- **WHEN** таблицю `orders` створено, і процес coordinator перезапущено
- **THEN** `GET /tables/orders` повертає `200` з тим самим визначенням

### Requirement: CREATE зберігає запис
Клієнт SHALL записувати запис (`PUT /tables/{table}/items`) з атрибутами ключа і полем `value` (JSON-об'єкт). Запис з тим самим ключем MUST замінювати попередній. Відповідь `201` MUST означати, що запис збережено довговічно.

#### Scenario: Запис у таблицю зі складеним ключем
- **WHEN** клієнт надсилає `PUT /tables/orders/items` з `{"userId":"42","orderDate":"2026-11-05","value":{"total":300}}`
- **THEN** відповідь `201`, і READ цього ключа повертає `{"total":300}`

#### Scenario: Перезапис
- **WHEN** клієнт удруге надсилає той самий ключ з `value` `{"total":150}`
- **THEN** READ повертає `{"total":150}`

#### Scenario: Таблиці нема
- **WHEN** клієнт пише в таблицю, яку не створено
- **THEN** відповідь `404`

#### Scenario: Бракує атрибута ключа
- **WHEN** у тілі запиту нема partition key або (для таблиці зі sort key) sort key
- **THEN** відповідь `400`, нічого не збережено

### Requirement: READ, EXISTS і DELETE за ключем
Клієнт SHALL читати (`GET`), перевіряти наявність (`HEAD`) і видаляти (`DELETE`) запис за адресою `/tables/{table}/items/{pk}/{sk}` (для таблиці без sort key — `/tables/{table}/items/{pk}`). Ключі в адресі передаються URL-encoded.

#### Scenario: READ наявного запису
- **WHEN** запис існує, і клієнт надсилає `GET /tables/orders/items/42/2026-11-05`
- **THEN** відповідь `200` з ключем і `value`

#### Scenario: READ відсутнього запису
- **WHEN** запису з таким ключем нема
- **THEN** відповідь `404`

#### Scenario: EXISTS
- **WHEN** клієнт надсилає `HEAD` на адресу запису
- **THEN** відповідь `200` без тіла, якщо запис є, і `404`, якщо нема

#### Scenario: DELETE
- **WHEN** клієнт надсилає `DELETE` на адресу наявного запису
- **THEN** відповідь `204`, а наступний `GET` повертає `404`

#### Scenario: DELETE відсутнього запису
- **WHEN** клієнт видаляє запис, якого нема
- **THEN** відповідь `404`

#### Scenario: Форма адреси не відповідає таблиці
- **WHEN** таблиця має sort key, а адреса без `{sk}` (або навпаки)
- **THEN** відповідь `400`

### Requirement: Query за partition key з діапазоном sort key
Для таблиці зі sort key клієнт SHALL отримувати всі записи одного partition key, впорядковані за sort key за зростанням, з опційними межами `skFrom` і `skTo` (обидві включно). Sort key порівнюється як рядок (лексикографічно).

#### Scenario: Діапазон дат
- **WHEN** для `userId=42` є записи з `orderDate` `2026-10-30`, `2026-11-01`, `2026-11-05`, `2026-11-07`, і клієнт надсилає `GET /tables/orders/items/42?skFrom=2026-11-01&skTo=2026-11-05`
- **THEN** відповідь `200` зі списком `[2026-11-01, 2026-11-05]` саме в такому порядку

#### Scenario: Без меж
- **WHEN** клієнт надсилає `GET /tables/orders/items/42` без `skFrom` і `skTo`
- **THEN** відповідь містить усі записи `userId=42`, впорядковані за sort key

#### Scenario: Partition key без записів
- **WHEN** для PK нема жодного запису
- **THEN** відповідь `200` з порожнім списком

### Requirement: Єдиний формат помилок
Кожна відповідь з кодом `4xx` або `5xx` (крім `HEAD`) MUST мати JSON-тіло `{"error":"<код>","message":"<опис>"}`.

#### Scenario: Помилка валідації
- **WHEN** клієнт надсилає тіло, що не є JSON
- **THEN** відповідь `400` з тілом `{"error":"bad_request","message":…}`

### Requirement: Недоступний шард не маскується
Якщо шард, що відповідає за ключ, недоступний, coordinator MUST відповідати `503` і MUST NOT відповідати `404` або читати з іншого шарда.

#### Scenario: Шард вимкнено
- **WHEN** процес шарда, відповідального за ключ, зупинено, і клієнт читає цей ключ
- **THEN** відповідь `503`
