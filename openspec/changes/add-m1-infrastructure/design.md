# Design

## Context

Мотивація і обсяг — `proposal.md`; вимоги — `specs/network/spec.md` і `specs/iam-readonly-access/spec.md`.

Поточний стан: репозиторій без інфраструктурного коду; в AWS-пісочниці нічого не створено. Обмеження, що формують підхід:

- AWS Academy Cloud Architecting Sandbox, `us-east-1`, профіль `kse-lab`; працюємо як сесія ролі `voclabs`; сесії ~3 год, ключі тимчасові.
- IAM-ресурси створювати не можна → описуємо і валідуємо, не деплоїмо.
- Бюджет $20 на весь курс → у M1 лише безкоштовні мережеві ресурси.
- IaC — CloudFormation, YAML (ADR-001).

## Goals / Non-Goals

**Goals:**
- Мережа, готова до M2 (точка входу) і M3 (3 репліки в 3 AZ) без перебудови.
- IAM read-only доступ, описаний кодом і перевірений статично.
- Повторюваний спосіб знести і підняти мережу з одного шаблону з заміром часу.
- Задокументовані з доказами: права ролі пісочниці, квоти для M2, бюджет M2.

**Non-Goals:**
- Жодних обчислювальних ресурсів (EC2, Lambda, контейнери) і точки входу (ALB / API Gateway) — це M2.
- NAT Gateway, VPC endpoints, bastion — не потрібні в M1 (і платні).
- Security groups і network ACL під конкретні сервіси — з'являться разом із сервісами в M2.
- IPv6.
- CI/CD — M2.

## Decisions

### 1. Стеки: мережа окремо від IAM і застосунку — ADR-002
`kv-network` (`infra/network.yaml`) деплоїться; `kv-iam` (`infra/iam-readonly.yaml`) лише валідується; стеки M2 беруть ID мережі через Export / `Fn::ImportValue`. Відкинуто: один стек (IAM відкотить мережу), nested stacks (зайвий S3-бакет, проблема IAM лишається).

### 2. Адреси: VPC `10.0.0.0/16`, 3 AZ, шість підмереж `/24` — ADR-003
Публічні `10.0.0–2.0/24`, приватні `10.0.10–12.0/24`; AZ через `Fn::GetAZs`; `MapPublicIpOnLaunch: false`. Відкинуто: 2 AZ (кворум M3 не переживе падіння AZ), менші/більші підмережі.

### 3. Маршрутизація
- Одна **публічна route table** з маршрутом `0.0.0.0/0 → IGW`, явно прив'язана до трьох публічних підмереж.
- Одна **приватна route table** лише з `local`, явно прив'язана до трьох приватних підмереж (за класифікацією лекції 3.2 — isolated subnets).
- **Main route table** VPC не змінюємо і ні до чого не прив'язуємо: так нова підмережа без явної прив'язки не стане публічною випадково.
- Одна route table на тип, а не на AZ: без NAT маршрути в усіх AZ однакові. Якщо в M2+ з'явиться вихід назовні по AZ, приватні таблиці розділимо.
- Відкинуто: маршрут до IGW у main route table (пастка: усі неприв'язані підмережі стають публічними).

### 4. Outputs і Exports мережі
Експортуємо `VpcId`, `VpcCidr`, ID кожної публічної і приватної підмережі, а також списки ID через кому (`PublicSubnetIds`, `PrivateSubnetIds`) з префіксом імені стека (`kv-network-…`). Префікс береться з `${AWS::StackName}`, щоб імена не залежали від ручного вводу.

### 5. Read-only доступ — ADR-004
Trust policy: лише інший акаунт (`TrustedAccountId`, параметр) з умовою MFA. Permissions: своя managed-політика — Allow на перегляд сервісів проєкту + explicit Deny на читання даних і секретів. Lambda як principal відкладено до M4–M5.

### 6. Як перевіряємо IAM без деплою
1. `aws cloudformation validate-template` — синтаксис шаблону.
2. `aws iam simulate-custom-policy` — передаємо JSON політики (витягнутий із шаблону) і дії зі сценаріїв spec; очікування: перегляд → `allowed`, запис/дані/секрети → не `allowed`; разом із політикою `s3:*` → `explicitDeny` на `s3:GetObject`.
3. Одна спроба `aws cloudformation deploy` стека `kv-iam`, щоб зафіксувати реальну помилку пісочниці (доказ для завдання 3); потім видалити стек у стані `ROLLBACK_COMPLETE`.
Відкинуто: ручна перевірка «на око» без інструменту — не доказ на захисті.

### 7. Розбір ролі пісочниці (завдання 1) — метод
Робимо разом, по кроку. Джерела від найменш до найбільш прямого:
1. Readme пісочниці (офіційний перелік дозволеного).
2. `aws sts get-caller-identity` — хто ми (ARN сесії ролі).
3. Спроба прочитати політики своєї ролі (`aws iam get-role`, `list-attached-role-policies`, `list-role-policies`, `get-role-policy`) — якщо дозволено.
4. `aws iam simulate-principal-policy` для дій, що нас цікавлять (якщо дозволено).
5. Проби з `--dry-run` (EC2) та безпечні спроби, що мають завершитися `AccessDenied` (наприклад, `iam:CreateRole`) — фіксуємо точний текст помилки.
6. Перевірка наявності `LabRole` / `LabInstanceProfile` та інших готових ролей (потрібні для M2).
Результат — `docs/m1/role-dissection.md`: що дозволено, що заборонено, якою командою це з'ясовано.

### 8. Квоти і бюджет (завдання 6–7) — метод
- Квоти: `aws service-quotas list-service-quotas` / `get-service-quota` для сервісів M2 (EC2 vCPU і Elastic IP, VPC, DynamoDB, Lambda, ELB, API Gateway — залежно від того, що реально може бути в M2) + обмеження з Readme пісочниці; фіксуємо поточні значення і чи можуть вони нас обмежити. Результат — `docs/m1/quotas.md`.
- Бюджет M2: розрахунок місяця для 2 шардів з явними припущеннями (тип обчислень, точка входу, зберігання, трафік, публічні IPv4, моніторинг) за цінами AWS Pricing на дату розрахунку; порівняння з $20 і що з цього випливає для дизайну M2. Результат — `docs/m1/budget-m2.md`.

### 9. Відтворюваність (завдання 8) — метод
Скрипт-послідовність: `delete-stack` → `wait stack-delete-complete` → `deploy` → `wait`/статус `CREATE_COMPLETE`, кожен етап з `time`; після — перевірки сценаріїв spec `network`. Записуємо час і все, що зламалося з першої спроби. Результат — `docs/m1/recreatability.md`.

## Risks / Trade-offs

- [Сесія пісочниці закінчилася посеред деплою] → CloudFormation продовжує працювати на стороні AWS; запускати деплой, коли до кінця сесії > 30 хв; після нового Start Lab перевірити статус стека.
- [`Fn::GetAZs` поверне AZ, де щось недоступно в пісочниці] → перед деплоєм `aws ec2 describe-availability-zones`; за потреби задати AZ параметрами.
- [Export блокує зміну/видалення мережі, коли M2 її імпортує] → видаляти у зворотному порядку; зміни експортованих значень — лише через оновлення споживачів.
- [Drift detection не бачить ресурсів, доданих руками поза стеком] → правило «нічого руками»; перевіряти зміни через change set.
- [Пісочниця забороняє `simulate-custom-policy`] → резерв: `aws accessanalyzer validate-policy`; якщо і він заборонений — задокументувати і перевірити політику явним розбором statement'ів; в будь-якому разі зафіксувати помилку як частину розбору ролі.
- [M2+ потребує ролей для сервісів, а створювати їх не можна] → у завданні 1 знайти готові ролі пісочниці; дизайн M2 будувати навколо них.
- [Вартість M2: публічні IPv4, ALB, трафік між AZ] → врахувати в `budget-m2.md`; serverless-точка входу як альтернатива ALB.
- [6 підмереж — більше YAML і пояснень] → однаковий шаблон для кожної пари, імена за схемою `public-a…c` / `private-a…c`.

## Migration Plan

Перша зміна, міграції даних нема.
- **Розгортання:** `aws cloudformation deploy --template-file infra/network.yaml --stack-name kv-network --profile kse-lab`; перед оновленнями — change set.
- **Відкат:** невдале створення відкочується автоматично; повний відкат — `aws cloudformation delete-stack --stack-name kv-network`.
- **IAM:** не розгортається (див. рішення 6).

## Open Questions

- Точний перелік дій у statement'і `ViewInfrastructure` — фіксуємо в apply, перевіряємо simulator'ом (не змінює підходу).
- Які готові ролі є в пісочниці (`LabRole` / `LabInstanceProfile`?) — відповідь із завдання 1, потрібна для M2.
